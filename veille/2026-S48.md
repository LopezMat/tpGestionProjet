### P-1 · Mettre à jour l'image PostgreSQL 16 (correctifs de sécurité 16.16)
- **Type** : `bug` (vulnérabilité).
- **Titre court** : « PostgreSQL : image 16.16 ou plus (43 CVE corrigées) ».
- **Priorité proposée** : `normale`. *Justification* : grille S2 § 4 (« CVE sans exploitation connue » = normale) et règle 2 (hors production = normale) ; aucune exploitation active signalée par postgresql.org ; pas d'exposition directe de secrets ou de données personnelles (exploitation par un utilisateur de base authentifié, et le SQL de l'app est statique). Version installée à confirmer. **Passe à `haute` au premier déploiement** si l'image n'est pas à jour : le ticket doit être `TERMINE` avant le GO (T-046), à ajouter aux dépendances du GO par le `chef-de-projet`.
- **Assigné proposé** : `agent:deployeur` (l'image vit dans `deploiement/docker-compose.yml`, **modèle commun DEC-003, responsable C**, utilisé par d'autres projets ; pas `dev-backend`).
- **Compétence requise** : `docker` (confirme) du référentiel de `equipe/agents.md` ; aucun agent du catalogue ne la liste, le `chef-de-projet` tranche l'affectation (`deployeur` : `ci-cd`, `sauvegarde-restauration`).
- **Estimation** : 1 h équivalent humain.
- **Description** : CVE : famille CVE-2026-120139 à CVE-2026-120154 et autres (43 identifiants au total dans les notes de la 16.16) ; paquet : PostgreSQL serveur (image `postgres:16-alpine`) ; version installée : **à confirmer** (tag flottant) ; versions corrigées : 16.16 et suivantes ; sources : [avis de sécurité](https://www.postgresql.org/support/security/), [notes 16.16](https://www.postgresql.org/docs/release/16.16/), [CVE-2026-120151](https://www.postgresql.org/support/security/CVE-2026-120151/) (CVSS 8,8, 2026-11-12) ; impact : exécution de code sur le serveur de base par un utilisateur authentifié, lecture ou suppression de toutes les données (réservations, comptes) ; preuve attendue : sortie de `SELECT version()` sur l'instance du projet.
- **Critères d'acceptation (vérifiables)** :
  - [ ] `SELECT version()` sur l'instance locale du projet affiche 16.16 ou plus (sortie collée au journal du ticket).
  - [ ] La version de l'image est fixée ou documentée dans le modèle commun (`postgres:16.16-alpine` ou procédure de `docker compose pull` dans le runbook), **après accord du responsable C** puisque le modèle est commun.
  - [ ] Le volume `pgdata` existant démarre sans dump/restore (mise à jour mineure) ; les migrations Alembic et la suite de tests passent sur l'image mise à jour.
  - [ ] Constat consigné : aucun index `GIN`, `bpchar` ni `gist_trgm_ops` dans les migrations (vérifié sur `0001_schema_initial.py`), donc pas de `REINDEX` ; et aucune extension C à reconstruire (à vérifier).
- **Revue humaine requise** : oui (sécurité, et modification d'un modèle commun).

### P-2 · Verrouiller les dépendances et figer l'image de base Python
- **Type** : `amelioration` (pratique ; reprend les constats 1 et 5 du rapport `securite-2026-11-25-3.md`).
- **Titre court** : « Verrou des dépendances avec empreintes, image Python figée, pip à jour ».
- **Priorité proposée** : `normale`. *Justification* : aucune faille connue sur les versions actuellement résolues (constats 5, 11, 12) ; le risque est la **dérive à la reconstruction** (FastAPI accepte `starlette>=0.46.0` alors que quatre avis Starlette de 2026 visent des versions plus anciennes que 1.3.1) et un pip éventuellement ancien (constat 6, à confirmer, `normale` au plus). Hors production : pas de `haute`. À faire avant le GO.
- **Assigné proposé** : `agent:dev-backend` (le `Dockerfile` et `requirements.txt` sont dans `app/`).
- **Compétence requise** : `docker` (confirme) ; `backend-python` en appui. Aucun agent ne liste `docker` : le `chef-de-projet` tranche.
- **Estimation** : 2 h équivalent humain (1 h de verrou avec empreintes, 0,5 h d'image et de pip, 0,5 h de documentation de la règle de reconstruction).
- **Description** : paquets concernés : Starlette, Pydantic et toutes les transitives, pip, image `python:3.14-slim` ; versions de référence : Starlette 1.10.0, Pydantic 2.14.4 (observées le 2026-11-25) ; versions corrigées des avis : Starlette 1.3.1 (CVE-2026-54283), 1.1.0 (CVE-2026-48818 et -48817), 1.0.1 (CVE-2026-48710) ; pip 26.2.0 (CVE-2026-13346) ; sources : [GitHub Advisory Database](https://api.github.com/advisories?ecosystem=pip&affects=starlette&per_page=20), [PyPI fastapi 0.162.7](https://pypi.org/pypi/fastapi/0.162.7/json), [PyPI pip](https://pypi.org/project/pip/) ; impact : une image reconstruite pourrait embarquer une dépendance vulnérable sans que rien ne le signale ; preuve : métadonnées de FastAPI (`starlette>=0.46.0`) et absence de fichier de verrouillage.
- **Critères d'acceptation (vérifiables)** :
  - [ ] Un fichier de verrouillage complet (transitives comprises, avec empreintes) existe, et le `Dockerfile` installe avec `pip install --require-hashes`.
  - [ ] Le fichier de verrouillage contient Starlette ≥ 1.3.1 (sortie `pip freeze` de l'image jointe).
  - [ ] L'image de base est fixée par digest (ou le choix du tag flottant est justifié par écrit), et `pip --version` dans l'image est ≥ 26.2.0 (ou pip est mis à jour dans le `Dockerfile`).
  - [ ] La règle de reconstruction (quand regénérer le verrou, qui lance `pip-audit`) est écrite dans la documentation d'exploitation du projet.
  - [ ] L'image se construit et la suite de tests passe.
- **Revue humaine requise** : oui (chaîne d'approvisionnement, sécurité).
