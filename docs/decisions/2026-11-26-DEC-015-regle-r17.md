## Contexte
[DEC-010](2026-11-24-DEC-010-principe-r17.md) a adopté R17 sur le principe et renvoyé sa réalisation à une PR de règles séparée, après le développement du projet client. Le contenu prévu est celui de [T-006](../../projets/reservation-coworking/tickets/T-006-ecritures-md-par-edit-uniquement.md), aujourd'hui `ANNULE` dans le projet client : texte de la règle dans `CLAUDE.md`, détection « si possible » dans `restreindre_bash.py`, un test par forme refusée, une lecture permise et le rejeu de l'incident DEC-007.

## Options étudiées
| Option | Avantages | Inconvénients |
|---|---|---|
| 1. R17 dans `CLAUDE.md` + détection dans `restreindre_bash.py` (option 1 de DEC-010, retenue) | la règle dit pourquoi, le hook l'applique, comme R5/R6 | analyse heuristique : un script enregistré puis lancé, `cp`, `mv` ou un chemin calculé à l'exécution lui échappent |
| 1a. Détection pour les seuls subagents | même périmètre que les autres contrôles du hook | ne couvre pas l'auteur de l'incident : la session principale |
| 1b. Détection pour tout appelant, session principale comprise (retenue) | couvre l'incident réel ; même portée que la confirmation du déploiement (DEC-003) | une lecture mal reconnue serait refusée : les formes de lecture courantes sont testées comme permises |

## Décision
1. **Règle R17 dans `CLAUDE.md`** : « Le coordinateur et les agents ne modifient jamais un document Markdown par Bash (sed, redirection, `tee`, script) : uniquement par Edit ou Write, pour que le hook R5/R6 s'applique. » Les scripts versionnés qui génèrent leurs fichiers (`tableau.py`, R9) ne sont pas concernés.
2. **Détection dans `.claude/hooks/restreindre_bash.py`, pour tout appelant** (session principale comprise), sur les fichiers `.md` de `docs/` et de `projets/`. Formes refusées :
   - `sed -i` (`-i.bak`, `-Ei`, `--in-place`) et `perl -i` ;
   - redirections `>` et `>>` (ainsi que `>|`, `&>`) ;
   - `tee` (avec ou sans `-a`) ;
   - scripts Python en ligne qui écrivent dans ces fichiers : `python -c`, `python -` ou `python` lisant un heredoc, un tube ou une here-string. Le script est refusé s'il nomme `docs` ou `projets` et un `.md`, et s'il contient une écriture (`write_text`, `.write(`, `open(…, "w"|"a"|"r+"|"x")`, `os.replace`, `shutil`, `subprocess`…) ;
   - les mêmes formes à l'intérieur de `bash -c`, `sh -c`, `eval`, `$( )`, d'un heredoc lu par un shell, d'une commande sur une nouvelle ligne, derrière `xargs`, `timeout` ou `find -exec`.
3. **Message** : « Refusé (R17) : … Utilise l'outil Edit ou Write : c'est le seul chemin que contrôle le hook R5/R6 (proteger_valide.py)… Une lecture (cat, grep, head, sed -n) reste permise. »
4. **Restent permis** : les lectures (`grep`, `cat`, `head`, `tail`, `sed -n`, `wc`, `git diff`, `git log`, un `python -c` qui lit), une redirection vers un fichier hors de `docs/` et `projets/`, `sed -i` sur du code, les scripts versionnés (`tableau.py`, `console.py`, les tests), et les messages de commit qui citent ces commandes, y compris en heredoc.
5. **Limites assumées**, rappelées dans le hook : un script Python enregistré dans un fichier puis lancé, `cp`, `mv`, `patch`, `git checkout` et un chemin construit à l'exécution ne sont pas analysés. R17 s'applique quand même, et `validations.yml` reste le filet pour le statut des documents.
6. **Tests** dans `scripts/test_restreindre_bash.py` (classe `TestR17`) : un test par forme refusée (`sed -i`, `>`, `>>`, `tee`, `python -c`, `python -` avec heredoc, Python sur un tube), les imbrications, les lectures et autres écritures permises, la confirmation du déploiement inchangée, et le **rejeu de l'incident DEC-007** (script Python par heredoc, `python -c` et `sed -i` sur DEC-007, `VALIDÉ`) refusé pour la session principale, fichier inchangé. Chaque forme est testée pour la session principale et pour un agent.
7. **ARCHITECTURE § 6** : garde-fou 9 ajouté (R17).

## Pourquoi
*(Ethan, 2026-11-24, DEC-010)*
- **Principe** : l'incident DEC-007 a montré qu'une écriture par Bash contourne le hook R5/R6 ; il n'a été détecté qu'après coup par `verifier_validations.py`.
- **Calendrier** : réalisation après le développement du projet client, dans une PR de règles séparée, parce que le client ne paie pas l'amélioration de nos outils internes (DEC-009, point D).
