# DEC-010 — Règle R17 adoptée sur le principe

> **En attente de validation humaine.** Le coordinateur a rédigé ce fichier à partir de la décision d'Ethan du 2026-11-24 sur T-050. Conformément à R5, c'est un membre de l'équipe qui le passe lui-même à `VALIDÉ` et renseigne `valide_par`. Le « Pourquoi » est celui formulé par Ethan (skill `tracer-decision`, étape 1).

## Contexte
Incident du 2026-11-24 : le coordinateur a modifié [DEC-007](2026-11-24-DEC-007-choix-techniques-coworking.md) par Bash alors qu'il était `VALIDÉ` (R6) ; le hook `proteger_valide.py`, qui ne surveille que Write et Edit, ne l'a pas bloqué, et seul `verifier_validations.py` l'a détecté (voir le [retex](../../projets/reservation-coworking/retex.md)). Ethan a demandé un ticket `amelioration` ([T-006](../../projets/reservation-coworking/tickets/T-006-ecritures-md-par-edit-uniquement.md)). Au tri, le `chef-de-projet` a posé le ticket [T-050](../../projets/reservation-coworking/tickets/T-050-modification-regle-r17.md) « Modification de règle R17 » (point d'arrêt humain : modification d'une règle, R7, R11). [DEC-009](2026-11-24-DEC-009-budget-delais-coworking.md) (point D) sort ce lot du projet client.

## Options étudiées
| Option (détail dans T-050) | Avantages | Inconvénients |
|---|---|---|
| 1. R17 dans `CLAUDE.md` + détection dans `restreindre_bash.py` (recommandée par le `chef-de-projet`) | la règle dit pourquoi, le hook l'applique, comme R5/R6 | le hook ne peut pas analyser un script enregistré dans un fichier puis lancé |
| 2. R17 seule | coût minimal | une consigne non appliquée techniquement a déjà été contournée |
| 3. Hook seul | protection technique | non justifiée par une règle (contraire à R11) |
| 4. Statu quo | aucun coût | le filet CI ne voit pas une modification du contenu d'un document correctement validé |

## Décision
1. **La règle R17 est adoptée sur le principe** : « Le coordinateur et les agents ne modifient jamais un document Markdown par Bash (sed, redirection, script) : uniquement par Edit/Write, pour que le hook R5/R6 s'applique. »
2. **Elle est réalisée après le développement du projet client**, dans une **PR de règles séparée**, qui contient aussi **la correction du skill `nouveau-projet`** (`hebergement: render` → `local`, DEC-003). Cette PR porte sa propre décision (`modifie_une_regle: oui`) et l'entrée de `docs/CHANGELOG-REGLES.md` (R11). Le contenu technique (détection dans `restreindre_bash.py` « si possible », demandée par Ethan à la création de T-006, soit l'option 1) y sera arrêté.
3. **T-050 passe `ANNULE`** avec la mention « déplacé vers les règles de l'ESN (PR de règles) » ; T-006, T-051, T-052 et T-053 aussi (DEC-009, point D).
4. **En attendant la PR**, le coordinateur applique déjà la règle à lui-même et la rappelle aux agents dans chaque lancement (modifications Markdown par Edit/Write uniquement).

## Pourquoi
*(Ethan, 2026-11-24)*
- **Principe** : l'incident DEC-007 a montré qu'une écriture par Bash contourne le hook R5/R6 ; il n'a été détecté qu'après coup par `verifier_validations.py`.
- **Calendrier** : réalisation après le développement du projet client, dans une PR de règles séparée, parce que le client ne paie pas l'amélioration de nos outils internes (DEC-009, point D).

## Impacts
- Fichiers ou règles à mettre à jour (dans la PR de règles, après le projet client) : `CLAUDE.md` (repassé `EN_REVUE` par un humain, R6), `.claude/hooks/restreindre_bash.py` et ses tests, `.claude/skills/nouveau-projet/SKILL.md`, nouveau fichier de décision, `docs/CHANGELOG-REGLES.md`.
- Tickets : T-050 passé `ANNULE` par l'humain (`decision: DEC-010`) ; T-006, T-051, T-052, T-053 passés `ANNULE` (DEC-009). Les tickets de la PR de règles seront recréés dans un projet interne de l'ESN.
- Règles : aucune modifiée par cette décision ; R17 entrera en vigueur avec la PR de règles.
